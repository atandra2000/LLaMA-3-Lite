01 / The system boundary

Three owners, one learning process.

The workspace shared_data package prepares the corpus. The project’s preparation shim adapts packed shards into the flat cache expected by its loader. The training runtime then owns model construction, optimization, evaluation and output artifacts. Keeping these responsibilities separate lets several models share corpus preparation without duplicating it.

Explore the complete system →

The learning path

A raw PyTorch decoder transforms token IDs into contextual hidden states. The separate output weight matrix maps those states into vocabulary scores. Cross-entropy measures next-token prediction error; backpropagation sends gradients through both the head and the decoder.

The observation path

Validation measures held-out loss. An exponential moving average (EMA) provides smoothed weights for evaluation and samples. Weights & Biases receives loss, learning rate, throughput and available GPU metrics. Checkpoints preserve training state for recovery.

02 / The model architecture

The residual stream carries the representation.

For batch size B and sequence length S, embedding lookup creates a [B, S, 1024] residual stream. Every decoder block adds two learned corrections: one mixes information across earlier token positions through attention; the other transforms each position through a feed-forward network. Pre-normalization controls the scale entering each branch.

Follow the decoder tensor flow →
x = embedding(token_ids)
h = x + GQA(RMSNorm(x))
x = h + SwiGLU(RMSNorm(h))   [repeat this block 16 times]
hidden = RMSNorm(x)
ComponentLocal implementation and purpose
RMSNormScale by the reciprocal root mean square, then apply a learned weight. It does not subtract the mean. Epsilon is 1e-5.
GQAQ has shape [B, 8, S, 128]; K and V begin as [B, 4, S, 128]. Each KV head serves two query heads. The local implementation expands K/V to eight heads before causal SDPA.
QK normalizationNormalize each projected query/key head before rotary position encoding. This controls scale entering attention and is enabled by default.
RoPERotate adjacent coordinate pairs in Q and K using position-dependent sinusoids. The frequency base is θ = 500,000. V is not rotated.
Causal SDPACompute softmax(QKᵀ / √128 + causal mask)V. The mask blocks future positions. PyTorch chooses a compatible backend; a fused FlashAttention backend is conditional on hardware, dtype and runtime support.
SwiGLUOne 1024 → 8192 linear projection produces gate and up halves, each width 4096. Compute SiLU(gate) × up, then project 4096 → 1024.
Untied output headThe output projection and input embedding are separate parameter matrices. At V = 128,000 each contains 131,072,000 parameters.

Training and generation have different output contracts.

Training calls model(input_ids, return_hidden=True). The loss receives hidden states, targets and the head weight, projects 256 rows at a time, and performs FP32 cross-entropy plus z-loss. Checkpointing each chunk recomputes its intermediates during backward instead of retaining all chunk logits.

L = mean over valid tokens of [−log p(target) + λ(log Σᵥ exp(logitᵥ))²]
λ = 0.0001   ·   ignored target = −100   ·   EOS remains learnable

Generation calls ordinary forward, which materializes vocabulary logits. It samples from the last position with temperature 0.8, top-k 50 and top-p 0.9, appends a token, and repeats until EOS or 128 new tokens. The current sampler recomputes the growing prefix: it has no persistent KV cache.

Do not equate architecture potential with implemented features. GQA reduces K/V projection parameters; a compact KV cache would benefit from the same grouping, but this generation loop does not implement one. Likewise θ = 500K is not a long-context API: the local RoPE cache is built for the configured 2048 positions.

The configured model has 513,840,128 parameters, including QK normalization. At startup, training uses max(config['vocab_size'], len(tokenizer)); a larger tokenizer therefore increases the two vocabulary matrices and the total count. This matters because special-token IDs can exceed the configured 128,000 base vocabulary.

03 / The data pipeline

Prepare documents once. Read token windows on demand.

Trace documents into training batches →

The canonical recipe lives in workspace LLM/shared_data/config/mixture.yaml. Its weights describe target token allocation, not measured downloaded volume. The legacy data_sources dictionary in the model config is not the preparation recipe.

  1. Prepare the corpus. Shared preparation downloads, filters and deduplicates text, then tokenizes and packs an EOS-separated uint32 stream. Character bounds and language heuristics are quality filters; SHA-256 exact deduplication does not detect paraphrases.
  2. Bridge the storage contract. The local shim sorts shard entries by manifest index and streams their bytes to a temporary cache file, then replaces tokens.bin atomically. Its read buffer is at most 2²⁶ tokens × 4 bytes, approximately 268 MB. Existing caches are reused by default.
  3. Map and partition. The loader opens the flat file read-only with NumPy memmap, aligns the split to 2049-token chunks and reserves the final approximately 5% for validation. Training windows are shuffled; validation stays ordered.
  4. Create the prediction pair. Each window is converted from uint32 to int64. Inputs are its first 2048 IDs; targets are the last 2048. Collation stacks samples into tensors, with pinned memory and nonblocking host-to-device copies on the training path.
Window: [A, B, C, EOS, D]
Input:  [A, B, C, EOS]
Target: [B, C, EOS, D]
Each target is the next token; EOS separates documents but is not masked out.
Mmap changes allocation behavior, not the laws of memory. An 8B-token uint32 file is about 32 GB on disk. Pages touched by readers can become resident; integer conversion, sampler permutations, worker queues and prefetched batches also consume RAM. “The whole file is not eagerly loaded” is accurate. “Only 1 MB of RAM is used” is not a guaranteed runtime property.

If the cache is missing, training warns and uses deterministic synthetic token data. If tokenizer loading fails, a byte stub is used and generated text is not meaningful. Validate tokenizer/cache compatibility before interpreting a run as real-corpus learning. Reusing an existing cache does not prove that it matches a changed recipe.

04 / The training pipeline

A gradient update is surrounded by a runtime.

Explore initialization, learning and persistence →

Initialization selects CUDA when available, otherwise CPU. CUDA setup enables the configured precision and allocator options. The runtime loads data, sizes the vocabulary, enforces the Triton opt-in gate, constructs the model and optionally compiles it in reduce-overhead mode. Compile warmup performs a real-shape forward and backward before the main loop.

AdamW applies weight decay 0.1 to trainable tensors with two or more dimensions, leaving one-dimensional normalization weights undecayed. Defaults are β₁ = 0.9, β₂ = 0.95 and ε = 1e-8. Linear warmup increases the learning rate from 3e-5 to 3e-4 across 2000 optimizer updates; cosine decay then approaches 3e-5.

stage next batch → BF16 forward on CUDA → chunked loss / accumulation
→ backward → [at accumulation boundary] clip global norm to 1.0
→ AdamW.step → EMA.update → zero_grad(set_to_none=True) → scheduler.step

The default accumulation factor is 1. The 42,000 loop iterations therefore process 8,257,536,000 token positions at batch 96 and sequence 2048, excluding warmup. This is a training exposure budget, not a count of unique corpus tokens. It exceeds the 8B prepared-corpus target, and the training split is smaller still.

Cadence checks use the zero-based loop variable with step > 0; the table states configured intervals, not an exact completed-update timeline for non-default accumulation.

What does resume restore—and what does it not guarantee?

The latest step checkpoint restores model, optimizer, LR scheduler, optional EMA and Python/NumPy/PyTorch/CUDA RNG state. It does not serialize sampler epoch or iterator position, so RNG restoration alone does not guarantee the identical next minibatch or loss curve. Checkpoint writes use torch.save directly; they do not have the temporary-file rename contract used by cache concatenation.

Observed implementation limits to keep separate from the intended flow

The compile warmup creates gradients before the loop, without a visible gradient clear before the first training backward. At corpus exhaustion, _next_batch constructs a fresh iterator but does not replace the caller’s exhausted iterator. These are source-level concerns for a training audit; the maps explain the intended repeated learning flow without treating long-run behavior as verified. No training code was changed for this guide.

05 / The optimization techniques

Reduce the right resource, at its owner.

Explore the resource map →

The “eight-technique memory stack” is a useful project label, but its mechanisms affect different resources. GPU activation memory, temporary logits, host RAM and matrix throughput cannot be added into one savings total. Several benefits overlap.

TechniqueMechanismCost or boundary
1. Gradient checkpointingRetain block inputs and recompute internal activations during backward.Trades extra compute for reduced retained activation memory.
2. Chunked head + CEProject 256 hidden-state rows at a time; checkpoint projection and loss.More chunks and recomputation. Chunking an already-created full logits tensor would not solve the main allocation.
3. Disk-backed token cacheRead uint32 pages as needed rather than creating a corpus-sized Python/tensor allocation.Disk I/O, resident pages, sampler memory and batch buffers remain.
4. BF16 autocastUse lower precision for eligible CUDA operations while model parameters remain FP32.Not every tensor is BF16; the loss promotes logits to FP32. No GradScaler is used.
5. FlashAttention via SDPAA compatible fused backend tiles attention rather than retaining the full score matrix.Backend selection is runtime-dependent. “Uses SDPA” alone is not proof of FlashAttention execution.
6. Grouped-query attentionFour K/V projections serve eight Q heads, halving K/V parameter count relative to eight KV heads.The current forward expands K/V for SDPA; no persistent inference KV cache exists.
7. Fused SwiGLU gate/upOne linear operation emits both gate and up activations.The PyTorch elementwise path remains the default; a custom Triton path is optional.
8. TF32 matmulsPermit Tensor Core arithmetic for eligible FP32 matrix multiplications on supported GPUs.A throughput option, not a reduction in stored FP32 bytes; no universal 3× speedup is promised.

Why the vocabulary head dominates a naïve implementation

Full logits, BF16: 96 × 2048 × 128,000 × 2 bytes = 50.332 GB
One 256-row chunk, BF16: 256 × 128,000 × 2 bytes = 65.536 MB
One chunk promoted to FP32: 256 × 128,000 × 4 bytes = 131.072 MB
768 chunks cover one default batch. These are tensor sizes, not measured peak memory.

For 513.84M parameters, FP32 parameters, gradients and two Adam moments alone total approximately 8.22 GB. A full FP32 EMA copy adds approximately 2.06 GB. Activations, loss temporaries, attention intermediates, allocator reserve and runtime workspaces sit on top. This explains why “BF16 training” does not imply two bytes per parameter for the complete training state.

Read the 92 → 20 GB headline as a documented estimate here. It implies a 78.3% reduction, but this work did not reproduce an A100 benchmark or reconcile every baseline assumption. The full-logit allocation alone demonstrates why baseline definitions matter. Compare measured allocated/reserved peaks at identical shapes, precision, EMA settings and warmup state before claiming a measured improvement.

Additional runtime and stability tools

torch.compile targets Python/launch overhead and graph optimization. Pinned memory, persistent workers and prefetch queues reduce input stalls. QK normalization, z-loss, gradient clipping and EMA address numerical behavior or evaluation noise; EMA increases memory. The allocator setting requests expandable segments, while cuDNN benchmarking is a configured option whose benefit is workload-dependent.

Three sanctioned Triton paths cover RMSNorm, SwiGLU and cross-entropy. Defaults are PyTorch. Enabling one requires its config selector to be triton and ENABLE_TRITON_KERNELS=1. The environment flag alone does not activate kernels. Explicit kernel failures surface; CPU reference tests do not establish GPU parity or speedup.
